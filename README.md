# DokeV — 도깨비와 친구가 되는 동네

> 설치도 로그인도 없이, 주소만 열면 시작하는 **브라우저 3D 어드벤처**.

## 게임 소개

한국형 도시의 한 동네다. 큰길과 골목, 시장과 언덕 주택가, 안개 낀 숲과 바닷가가
이어져 있고, 그 사이에 **도깨비**가 숨어 있다.

도깨비는 잡는 것이 아니라 **친해지는 것**이다. 넷이 있고 저마다 나타나는 조건이
다르다 — 그냥 따라오는 아이가 있는가 하면, 말썽 부리는 장난감 로봇을 여럿
멈춰야 나타나는 아이도, 여정을 끝까지 마쳐야 만나지는 아이도 있다. 조건을 채우면
지도에 자리가 뜨고, **그 자리까지 가야** 만나진다.

도깨비는 **평소에는 나와 있지 않다.** 말썽 부리는 로봇이 가까워지면 나타나고,
싸움이 끝나면 잠깐 곁에 남았다가 물러난다.

함께 있는 동안 능력을 하나씩 준다. 숨은 흔적을 잠깐 빛나게 하고, 연기로 몸을
감추고, 상처를 씻고, 골목 구석까지 한꺼번에 밝힌다.

### 무엇을 하는가

- **달린다.** 걷고 달리고, 킥보드·자전거·스케이트보드·장난감 자동차·조랑말을 탄다
- **건너다닌다.** 이단 점프, 떨어지며 활강, 가로등에 그래플로 붙어 옥상을 넘는다
- **막는다.** 장난감 방망이·고무 망치·딱총으로 말썽 부리는 고물 로봇을 멈춘다.
  쓰러진 로봇에서는 갇혀 있던 빛이 빠져나간다
- **논다.** 자판기에서 음료를 뽑고, 부두에서 낚시를 하고, 광장에서 춤을 추면
  지나가던 사람들이 따라 춘다
- **남긴다.** 포토 모드로 시간대와 색을 골라 사진과 클립을 찍는다

### 이런 게임이다

- **죽지 않는다.** 실패해도 벌이 없다. 놓치면 다시 하면 된다
- **여정은 저장된다.** 단계·처치 수·만난 도깨비는 브라우저에 남는다.
  서 있던 자리는 남지 않아 다시 들어오면 광장에서 시작한다
- **시간이 흐른다.** 여명·한낮·노을·밤. 밤이면 창문과 가로등이 켜지고 거리가 빈다
- **키보드도 터치도 된다.** 조작 전부에 터치 버튼이 있다

한국 설화와 현대 도시에서 출발한 **독자 IP 창작물**이다. 펄어비스 「도깨비」
트레일러에서 받은 인상을 웹에서 가능한 범위로 옮겨 본 프로젝트이며, 특정 상용
게임의 공식 서비스가 아니다.

## 시작하기

```bash
pnpm install
pnpm dev
```

http://localhost:3112 를 연다. (포트는 `package.json`의 dev 스크립트를 따른다.)

## 어떻게 노는가

**목표는 도깨비 넷과 친구가 되는 것이다.** 잡는 것이 아니라 친해지는 것이라,
각자 원하는 조건이 따로 있다. 도시를 달리고, 말썽 부리는 장난감 로봇을 멈추고,
골목에 남은 흔적을 살피다 보면 하나씩 나타난다.

죽지 않는다. 실패해도 벌이 없다 — 놓치면 다시 하면 된다.

### 조작

| | 키보드 | 터치 |
|---|---|---|

| 활강 | **높은 곳에서** 떨어질 때 `Space` 유지 (`G`로 가로등에 올라가면 된다) | 점프 버튼 길게 |
| 공격 | `J` | 공격 버튼 |
| 무기 바꾸기 | `Q` | — |
| 그래플 | `G` (가로등을 보고) | 그래플 버튼 |

| 포토 모드 | `P` (`Z`/`X`로 거리 조절) | — |

### 첫 여정

처음 들어가면 「첫 번째 산책」이 순서대로 안내한다. 안내를 따라가면 이 게임이
가진 이동 수단을 한 번씩 다 써 보게 된다:

1. `Shift`로 달려서 몸을 풀고
2. `B`로 스케이트보드를 꺼내 동네 반대편까지 가고
3. 말썽 부리는 장난감 로봇을 `J`로 멈추고
4. 높은 곳에서 뛰어내려 `Space`를 유지해 활강하고
5. `G`로 가로등에 붙어 건너다니고
6. 지도의 노란 마름모 자리에서 `T`로 흔적을 살핀다

그 뒤 지도에 붉은 삼각형이 서면 **고물 대장**이 기다리는 자리다. 바닥에 링이
퍼지면 물러서고, 휘두른 뒤 빈틈에 때린다.

### 도깨비 넷

| 도깨비 | 능력 | 친해지는 조건 |
|---|---|---|
| 초롱 | 반딧불 — 주변에 숨은 흔적을 잠깐 빛나게 한다 | 처음부터 함께 있다 |
| 그을음 | 잿불 — 연기로 몸을 감춰 로봇이 잘 알아보지 못한다 | 장난감 로봇 12기 |
| 물비늘 | 물무늬 — 상처를 씻어 빠르게 아물게 한다 | 첫 여정을 끝까지 |
| 자정 | 먼 불빛 — 골목 구석까지 한꺼번에 드러난다 | 고물 대장을 눕히면 |

조건을 채우면 지도에 자리가 뜨고, **그 자리까지 가야** 만난다. 조건만 채우고
가지 않으면 아직 만난 것이 아니다.

## 커밋 전 검증

```bash
pnpm verify
```

`typecheck → lint → build → test` 순으로 돈다. 타입 오류를 먼저 잡는다는
원칙은 그대로고(타입 1초, 린트 1초), **빌드를 테스트 앞에 둔다**.

번들 크기 검사가 `.next`를 읽기 때문이다. 예전 순서에서는 새로 받은
저장소에 `.next`가 없어 그 검사가 **조용히 건너뛰어졌고**, 있더라도 직전
빌드를 재고 있었다 — 무거운 의존성을 더해도 그 반복에서는 안 걸린다.
빌드가 2초라 순서를 바꿔도 피드백이 느려지지 않는다.

넷 중 하나라도 실패하면 커밋하지 않는다.

개별로도 돌릴 수 있다:

| 명령 | 하는 일 |
|---|---|
| `pnpm typecheck` | `tsc --noEmit` |
| `pnpm lint` | `biome check src tests` (서식 + 린트) |
| `pnpm format` | 같은 것을 고쳐 쓴다 (`--write`) |
| `pnpm build` | 프로덕션 빌드 |
| `pnpm test` | vitest 1회 실행 (번들 검사는 `.next`가 있어야 돈다) |
| `pnpm test:watch` | 파일 변경 감시 |

## 확인해 볼 곳 (개발 빌드)

```
/play?see=demo    시연 1분 30초 — 코스 첫 장면에서, 전부 열린 채로
/play?see=boss    미니 보스 앞 — 예고 링과 크기감
/play?see=summon  보스전 합동 공격 — 도깨비 넷이 도는지, 능력 자국이 보이는지
/play?see=ability 도깨비 능력 VFX — 장애물 없는 시작 지점에서 단독 확인
/play?see=night   밤 — 창문·가로등·전조등 밝기
/play?see=noon    한낮 — 색이 날아가는지, 그림자 길이
/play?see=air     공중 — 높은 곳에서 떨어지고 활강하는 감각 (실루엣이 묻히지 않는 것은 확인됨)
/play?see=result  완주 화면 — 두 번째 완주에도 다시 뜨는지 (한 화면에 담기는 것은 확인됨)
/play?see=party   도깨비 4종 동행 — 대열이 보기 좋은지 (겹침·색 구분은 확인됨)
/play?see=clues   흔적 조사 — 흔적 원반의 크기가 알맞은지 (마름모·살펴보기는 확인됨)
/play?see=shrine  도깨비 자리 앞 — 빛기둥이 눈길을 끄는지 (보이는 것은 확인됨)
```

능력 VFX를 하나씩 볼 때는 능력 확인 주소에 도깨비 id를 붙인다. 예를 들어
`/play?see=ability&dokebi=mulbineul`은 물비늘만 동행한 상태로 연다. 쓸 수 있는
id는 `chorong`, `geueum`, `mulbineul`, `jajeong`이다.

프로덕션 빌드에서는 동작하지 않는다. 이 목록은 `devScenario.ts`의 정본과
어긋나면 테스트가 막는다 — 실제로 한 번 낡았다.

`?see=demo`는 **1분 30초 시연 코스**다. 화면 왼쪽 위에 지금 장면과 눌러야 할
키가 뜬다. 촬영 대본은 [docs/DEMO_SCRIPT.md](docs/DEMO_SCRIPT.md)에 있고,
그 표는 코스 정본(`demoRoute.ts`)에서 옮긴 것이다 — 구간마다 「그 시간 안에
실제로 갈 수 있는가」를 검사가 대조한다.

**한 방향으로만 흐른다 — 확인 지점은 저장을 바꾸지만, 저장은 확인 지점을 바꾸지
않는다.**

- **확인 지점 → 저장**: 여기서 한 일은 그대로 기록된다. `?see=party`를 한 번 열면
  그 뒤의 `/play`는 도깨비를 다 만난 상태로 시작한다. 개발 중에만 생기는 일이지만
  「목표가 안 뜬다」고 헤매기 전에 알아 두면 좋다.
- **저장 → 확인 지점**: 흐르지 않는다. 여정 단계·완주 여부·만난 도깨비·찾은 흔적은
  **링크가 정해 주므로**, 이미 완주한 판을 갖고 있어도 `?see=clues`에는 흔적 세 곳이
  그대로 있고 `?see=shrine`에는 빛기둥이 서 있다. 처치 수·대장 기록 같은 여정 밖의
  기록과 시간대 취향은 그대로 따라온다.

한동안 이 두 번째가 새고 있었다 — 완주 화면이 앞을 가리거나, 볼 것이 하나도 없는
확인 지점이 열렸다. 같은 종류로 다섯 군데였다.

## 사람이 봐 줘야 하는 것

브라우저 자동화로 연 탭은 `document.hidden`이라 시간이 스크린샷을 찍는 동안에만
흐른다. 그래도 페이지 안에서 키 이벤트를 보내면 **달리게 할 수는 있다** — 그렇게
이동·추격·여정 진행은 확인했다. 남은 것은 **연속적인 감각**이다: 가속이 시원한지,
관성이 자연스러운지, 부딪힐 때 무게가 실리는지
(근거: [RALPH_BACKLOG.md](./docs/RALPH_BACKLOG.md) 「브라우저 자동화의 한계」).

**단위 검사가 원리적으로 못 보는 자리가 딱 둘 남았다.** 씬이 프레임 사이에
플레이어 상태를 들고 있는 참조(`locomotion.current`)에 쓰는 두 줄이다. 지우면
**아예 못 움직이거나 부활이 안 되는데**, 그 참조는 컴포넌트 안에만 있어 값으로
잴 데가 없다. 브라우저에서 한 걸음 걸어 보는 것이 이 둘의 유일한 검사다 —
그래서 이 목록의 1번이 그 역할을 겸한다.

처음엔 「2분」이라고 적어 두었는데, 그 사이 항목이 열다섯 개가 됐다. 다 보려면
15분쯤 걸린다 — **거짓 시간표는 아무도 시작하지 않게 만들므로** 나눠 둔다.

### 2분: 이것만은

**「도는가」는 이제 자동화로 확인했다.** 달리기·시점 드래그·보드가 실제로 동작하고
여정 단계가 넘어가는 것까지 봤다(방법은 백로그의 「브라우저 자동화의 한계」). 남은
것은 **연속적인 감각** — 자동화는 스크린샷을 찍는 동안에만 시간이 흐르므로
가속·관성·타격감은 원리적으로 볼 수 없다. 다섯 개만 보고 덮어도 된다.

1. `/play` — `W`를 **누른 채로** 달린다. 움직이는 것은 확인했다. 물어볼 것은
   **속도가 붙는 느낌**과 카메라가 따라오는 거리감이다.
2. 화면을 **드래그**해 시점을 돌린다. 도는 것은 확인했다. 물어볼 것은 **감도**다.
3. `Shift` 달리기 → `B` 탈것(거치대 곁이면 킥보드·자전거, 아니면 스케이트보드) → `G`로 가로등에 붙었다가 뛰어내려 `Space`를 누른 채 활강.
   (평지에서 뛰면 0.62초, 2단 점프로도 0.83초뿐이라 여정 목표 1.5초에 닿지 않는다.
   높은 데서 뛰어내려야 한다 — 그래서 힌트도 가로등을 말한다.)
   **셋 다 화면으로 확인했다** — `G`를 누르면 8m/s로 가로등 높이까지 끌려 올라가고,
   그 상태에서 `Space`를 누르고 있으면 간판보다 높은 곳에서 팔을 벌린 자세로 떠서
   내려온다. 물어볼 것은 **감각**이다: 끌려가는 맛이 나는지, 활강이 너무 느리거나
   빠르지 않은지.
4. `/play?see=boss` — 보스가 다가와 바닥에 링을 그리는가. `J`로 때려 이길 수 있는가.
   **규칙은 검사가 증명한다**(다가옴·예고·충격·빈틈·비틀거림·쓰러짐, `bossSim.test.ts`).
   못 본 것은 **화면과 손맛**이다: 링이 제때 보이는지, 때린 느낌이 나는지, 피할 시간이
   실제로 있는지. 자동화로 붙어 보려 했지만 스크린샷 한 번에 5~7프레임밖에 안 돌고
   프레임당 시간이 1/30초로 잘린다(`MAX_DELTA_SECONDS`) — 대장은 프레임마다 7cm씩만
   다가오고, 이쪽에서 달려가려면 시점부터 돌려야 한다. 사람은 3초면 닿는 거리다.
5. `F3` — FPS가 뜨는가(「아직 재는 중」에서 안 바뀌면 탭이 숨은 것이다).

**1번은 겸사겸사 다른 것도 확인해 준다.** 씬이 프레임 사이에 플레이어 상태를
들고 있는 참조에 쓰는 두 줄은 **단위 검사가 원리적으로 못 본다**(위 「사람이 봐
줘야 하는 것」 머리말 참고). 한 걸음 걸어서 속도계가 0이 아니면 그 둘이 살아
있다는 뜻이다 — 자동화로도 봤지만(2.6 m/s), 사람이 걸을 때마다 다시 확인된다.

이 다섯을 보면 화면으로 고친 것들(카메라 시작 각, 밤 조명, 빛기둥 밝기,
HUD 배치)도 함께 확인된다.

### 이번에 새로 생긴 것 (같이 봐 주면 좋다)

- **자정** — 고물 대장을 눕히면 자리가 드러나는 네 번째 도깨비. `/play?see=party`로
  넷을 한 화면에서 볼 수 있다. **자리 배치와 색 구분은 화면으로 확인했다** —
  넷이 고리까지 안 겹치고 갈라진다. 「모퉁이에서 뭉치는가」도 사람에게 물어보려다
  검사로 옮겼다(급회전에서 1.39m까지만 좁아진다). 남은 것은 **그 대열이 예쁘냐**는
  취향 문제뿐이다.
- **완주 화면** — `/play?see=result`. 셋 중 **하나만 남았다.**
  「만난 도깨비」 수는 **화면으로 확인했다** — 가득 찬 상태로 뜬다. 분모는
  **찾아갈 수 있는 수**다. 초롱은 처음부터 함께 있어 만남 목록에 들어가지 않으므로,
  전체 수로 세면 다 모아도 가득 차지 않는다 — **도감과 분모가 다른 것은 그래서 맞다.**
  **기록이 그 순간에 굳는지**와 **한 번 닫은 뒤 다음 여정을 마쳐도 다시 뜨는지**는
  장치가 코드에 있다는 것까지만 검사가 붙들고 있다(`완주한 순간의 값을 굳힌다`,
  `두 번째 완주에도 화면이 뜬다` — 둘 다 **소스를 읽는 검사**라 실행 결과는 못 본다).
  실제로 두 번째 완주까지 가 본 사람이 아직 없다 — **이것만 봐 주면 된다.**
- **말 걸기·살펴보기** — 주민이나 간판 **바로 앞**에서 `T`(터치는 「살펴보기」).
  **길 한가운데서는 안 뜬다** — 손 닿을 거리까지 붙어야 한다(가게 앞을 스치듯
  지나며 확인하려다 「안 뜬다」고 오해할 뻔했다). 물어볼 것은 그 거리가 **답답하지
  않은지**, 가까이 갔을 때 화면이 먼저 알려 주는지, 누르면 한 줄이 뜨는지다.
- **반딧불로 흔적 찾기(새로 생김)** — `/play?see=clues`에서 `E`를 누르면 동료
  빛이 닿는 곳의 흔적이 **바닥에 노란 원반으로 떠오른다**(지도 마름모와 같은 색).
  드러나는 범위는 도깨비마다 다르다 — 자정은 넓게, 그을음은 오히려 좁게. 나오는
  것은 확인했고, 물어볼 것은 **원반이 눈에 띄면서도 길을 안 가리는 크기인지**다.
- **민트 후드 + 물비늘** — 시작 화면에서 민트를 고르고 물비늘을 데리고 다녀 보라.
  둘 다 청록 계열이라 색거리가 55다(예전에 41을 「같은 보라색」이라며 고친 적이 있다).
  나와 동료가 한눈에 갈리는지, 아니면 두 덩어리로 뭉쳐 보이는지가 이 조합의 질문이다.
- **흑백·또렷하게가 이 도시에 어울리는가(새로 생김)** — 포토 모드에서 골라 보라.
  **작동은 확인했다**: 화면이 흑백으로 바뀌고, 저장 경로와 같은 합성을 돌려 픽셀을
  읽어 보니 원본은 컬러인데 결과는 완전한 회색이었다(R=G=B). HUD는 컬러로 남아
  버튼이 그대로 읽힌다. 물어볼 것은 **취향**이다 — 밤 골목이 흑백으로 좋은가,
  대비 보정을 더 올릴까 내릴까, 「또렷하게」의 채도가 과하지 않은가.
- **가장자리에서 찍기** — 포토 모드에서 「몽환」을 켜고 노을에, 캐릭터를
  화면 **가장자리**로 밀어 찍어 보라. 비네트가 인물과 배경을 함께 어둡게 해
  색거리가 52 → 23으로 떨어진다(가운데는 43으로 버틴다). 형태가 남는지가 질문이다.
- **소리로 구분되는가** — 적을 때릴 때(320Hz)·내가 맞을 때(520Hz)·적이 쓰러질 때
  (180Hz)·보스가 내려칠 때(90Hz)가 서로 다른 소리로 들리는가. 값은 갈라 두었지만
  **아무도 들어 본 적이 없다.** 자동화로는 원리적으로 못 듣는다 — 자동화 탭은
  `hidden`이라 오디오 엔진이 아예 시작하지 않는다(그게 맞는 동작이다).
- **소리가 한 바퀴마다 「틱」 하는가** — 바람·도시 웅웅거림은 2.5초짜리 소리를
  반복해 만든다. 경계를 이어 붙여 두었지만 **그게 실제로 통했는지는 값으로
  확인할 수 없다.** 조용한 데 서서 몇 바퀴 들어 보면 안다.
- **반딧불·춤·동료 해제(E·R·C)** — **동작은 확인했다**: 동료가 밝아지며 바닥에
  빛웅덩이가 생기고, 춤 자세로 바뀌면 초롱이 「누가 보면 어때.」로 받아치고,
  해제하면 즉시가 아니라 작아지며 사라진다. 물어볼 것은 **느낌**이다 — 빛이
  충분한지, 춤이 BPM 96과 맞아 보이는지, 사라지는 0.35초가 적당한지.


## 화면으로 확인 못 한 수정

**이번에 고친 것 중 화면으로 확인 못 한 것이 셋 있다.** 전부 값으로는 맞는데
브라우저 확장이 연결돼 있지 않아 눈으로 보지 못했다:

- **GLB 캐릭터의 높이** — 이 모델은 발바닥이 원점인데 플레이어 그룹의 원점은
   몸의 가운데다. 보정을 빠뜨려 **키의 절반만큼 떠 있었다.** 지금은
   `-PLAYER_HEIGHT / 2`를 준다.
- **GLB 동작 전환** — 씬이 매 프레임 갱신하는 공유 객체를 `{ ...stats }`로
   **복사해서** 넘기고 있었다. 그러면 React가 리렌더할 때만 동작이 바뀐다.
   지금은 참조를 그대로 넘긴다.
- **탈것이 보이는지** — 보드가 절차적 캐릭터 **안에** 있어서 GLB로 탈 때는
   아무것도 안 보였다. 밖으로 꺼내 형제로 올렸다.

## 검사가 정말 잡는지 확인하려면

```bash
scripts/mutate.sh <파일> '<찾을 문자열>' '<바꿀 문자열>' all '<설명>'
```

소스를 잠깐 결함 형태로 되돌리고 검사가 **실패하는지** 본다. 통과하면 그
검사는 지키는 척만 하고 있는 것이다.

**이게 이 저장소에서 가장 값진 도구다.** 한 세션에 스물한 번 뚫어 **다섯 구멍**을
찾았고, 다섯 다 코드를 읽어서는 안 보였다 — 검증 코드도 있었고 검사도 있었다.
다만 그 검사가 그것을 보지 않았을 뿐이다.

아래 규칙들이 이 도구를 쓰며 하나씩 나왔다. 길어졌으니 먼저 어디를 볼지 고르라:

| 무엇을 하려는가 | 아래에서 찾을 말 |
|---|---|
| **표적을 고른다** | 「사용자에게 한 약속」·「실패해도 옆에서 됐다고 말하는 자리」·「주석이 못 박았는데 아무도 안 지키는 규칙」·「검사에 이름조차 안 나오는 소스」·「이름조차 부른 적 없는 export」·「같은 규칙이 두 자리에」·「한 곳에서 찾은 모양은 이웃에도」 |
| **크게 쓸어낸다** | 「배선은 손으로 찾지 말고 쓸어내라」·「변이 훑기에는 한 번당 시간 제한을」 |
| **결과를 읽는다** | 「헛돎이 나오면 두 가지를 본다」·「지워도 모른다가 늘 결함은 아니다」·「소스 모양 검사가 깨지면 결함인지 이사인지」 |
| **검사를 쓴다** | 「어딘가 한 군데만 맞으면 통과」·「초기값을 기대값과 다르게」·「서식에 기대는 것」·「규칙이 결함 아닌 것을 물면」·「이름 규칙으로 만든 검사는 이름 자체도」 |
| **쓰고 나서 확인한다** | 「사례 전부에 변이를 걸라」·「반대쪽도 재 보라」 |

도구도 셋 있다 — `tests/support/stale.ts`(초기값이 기대값과 같아 눈머는 것을
막는다), `tests/support/bothWays.ts`(한쪽만 재는 것을 막는다),
`tests/support/readsAll.ts`(**검사가 읽지 않는 칸**을 찾는다). 규칙을 기억에
맡겼다가 같은 실수를 반복해서 옮겨 둔 것들이다.

**무엇을 뚫을지는 「사용자에게 한 약속」에서 고른다.** 그렇게 골랐더니 나온 것들:

| 뚫린 약속 | 무슨 일이 났나 |
|---|---|
| 저감 모션 | 군중·도깨비 자리의 흔들림 게이트를 지워도 통과. 흔들림에 예민한 사람이 켜 둔 설정이 무력해도 몰랐다 |
| 음소거 | 재생 판단에서 소리 설정을 빼도 통과. 소리를 못 끄면 게임을 끄는 수밖에 없다 |
| 손상된 저장 | 여정 id가 숫자여도 그대로 흘러들었다. 진행을 잃은 것처럼 보인다 |
| 도시 결정성 | 씨앗에 시간을 섞어도 왕복 검사가 통과했다 — **연달아 두 번** 부르므로 밀리초가 같다 |

**적중률이 가장 높았던 기준은 따로 있다 — 「실패해도 옆에서 무언가가 『됐다』고
말해 주는가」.** 조용한 실패보다 **거짓 신호가 있는 실패**가 훨씬 늦게 발견된다.
이 기준으로 다섯을 찾았다:

| 거짓 신호 | 실제로는 |
|---|---|
| 「그래픽 품질을 보통으로 낮췄습니다」 | 그림자가 계속 켜져 있어 프레임이 안 돌아온다 |
| 캐시가 쌓인다 | 아무도 안 읽어 텍스처가 매번 새로 생긴다 |
| 게임이 평소처럼 돈다 | 저장이 막혀 진행이 하나도 안 남는다 |
| 「…저장됨」 + `photo_saved` 기록 | 내려받기가 실패해 파일이 없다 |
| 「…저장됨」 + `clip_saved` 기록 | 0바이트짜리 열리지 않는 파일 |

반대로 잘 지켜지던 곳도 많다(포토 모드 정지·그래플 사거리·지도 방향·설정 검증).
**뚫어 보지 않으면 어느 쪽인지 알 수 없다.**

한계도 알아 두라: 문자열 치환이라 **글자를 남긴 채 동작만 바꾸는 변이**를 만들기
어렵다. 그래서 소스를 읽는 검사(래칫)는 실제보다 튼튼해 보인다.

**개수를 잴 때는 「0보다 많다」가 아니라 「무엇당 몇 개인가」로 재고, 한 통에
여러 출처가 섞여 있는지 보라.** 이 세션에 네 번 헐렁했다 — 줄무늬는 바깥 구역에만
생겨도 수백 개였고, 옥상은 실외기를 죽여도 물탱크가 남았고, 현수막은 도로 쪽을
통째로 죽여도 건물 벽 것이 남았다. **세는 것만으로는 어느 출처가 죽었는지 모른다.** 이 세션에
여러 번 헐렁했다 — 횡단보도 줄무늬 경계를 뒤집어 **바깥 구역에만** 생기게 해도
수백 개가 남아 통과했고, 「구역당 몇 줄」로 바꾸니 걸렸다. 무엇으로 나눌지
(구역당·초당·자리당)를 먼저 정해야 개수에 뜻이 생긴다.

**검사를 새로 쓸 때 가장 흔한 약점은 「어딘가 한 군데만 맞으면 통과」다.** 파일
전체에서 `toContain("quality.fogFar")`를 찾으면 안개가 쓰고 있으니 **카메라 쪽을
박아도 통과**하고, 캐시 적중을 하나만 확인하면 **셋 중 하나를 뚫어도 통과**한다.
같은 이름이 여러 번 나오는 파일에서는 반드시 샌다 — **구간을 나눠 각각 보거나,
개수를 맞춰라**(읽는 곳 수 = 돌려주는 곳 수). 두 번 다 이 방식으로 잡혔다.

**이름 규칙으로 만든 검사는 이름 자체도 검사하라.** 「`project`·`record`·`reset`·
`consume`으로 시작하는 함수는 프레임 루프에서 불려야 한다」는 규칙을 만들었더니,
`takeDiscovery`라고 지은 함수를 **아예 못 보고 지나쳤다**. 지금은 「넘겨받은
객체를 고치는 함수는 넷 중 한 동사여야 한다」가 그 구멍을 막는다.

**소스 모양에 기댄 검사가 깨지면 「결함인지 이사인지」부터 가르라.** 이 세션에
다섯 번 깨졌고 다섯 번 다 이사였다 — 코드를 좋은 방향으로 옮길수록 그렇게 된다.
검사를 따라 옮기면 다음 이사에 또 깨진다. **값으로 재거나, 「하는 일」로 찾게**
고치라: 「`link.playerHp`를 대입하는 파일」이 아니라 「체력을 다루는 파일」로.

**변이 훑기에는 한 번당 시간 제한을 걸라.** 변이는 「틀린 답」뿐 아니라
**「답이 없음」**도 만든다 — 비교 방향을 뒤집으면 각도 정규화 `while`이 무한
반복이 되고, 검사가 실패하는 대신 **끝나지 않는다.** 제한이 없으면 훑기가 거기서
멈추고, 죽으면서 그 변이를 소스에 남긴다(실제로 겪었다). 안 끝나는 것도 「잡았다」로
세면 된다.

**「헛돎」이 나오면 두 가지를 본다: 변이가 진짜 결함인가, 그리고 탐침이
실제로 적용됐는가.** 이 세션에 탐침이 빗나간 것만 세 번이다 — 없는 줄을 찾거나,
인자를 엉뚱한 자리에 넣거나, 단락 연산으로 이름만 남겼다. 셋 다 「검사가 뚫렸다」로
보였지만 **뚫린 것은 탐침**이었다.

**「지워도 모른다」가 늘 결함은 아니다 — 조건문에서는 특히.** 대입을 지워서
아무도 모르면 거의 결함이지만, 조건은 **일어날 수 없는 상태를 막는 방어선**일 수
있다. 그때 할 일은 방어선을 지우는 것도, 못 미더운 검사를 만드는 것도 아니라
**왜 안 밟히는지를 검사로 못 박는 것**이다. 전제가 깨지면 거기서 먼저 걸리고,
그때부터 방어선이 진짜 일한다.

**규칙 하나를 쓰면 그 규칙이 지키기로 한 사례 전부에 변이를 걸라.** 한 사례만
확인하면 규칙의 구멍이 남는다 — 배선 규칙을 만들 때 첫 사례가 마침 정의가
`.ts`에 있어서, **정의 파일이 `.tsx`면 자기 정의를 호출로 세는** 버그가 두
반복 뒤에야 드러났다. 열 사례에 전부 걸어 보는 데는 몇 분이면 된다.

`tests/support/stale.ts`의 `staleCopy(원본)`을 쓰면 된다 — 모든 칸이 원본과
다른 객체를 만들어 준다. 손으로 적으면 어느 칸 하나가 기대값과 같아져도 모른다.

**화면 칸을 재는 검사는 초기값을 기대값과 다르게 두고, 불리언은 두 방향을 다 재라.** 빈 문자열·0·false로
시작하면 **안 채운 것과 채운 것이 같아 보인다** — 실제로 `counter`와 `completed`가
그렇게 통과했다. `"아직-안-채움"`·`-1`·반대 불리언으로 시작하면 안 채운 칸이
그대로 남아 눈에 띈다. 불리언은 값이 둘뿐이라 한 방향만 재면 절반은 늘 통과한다 —
`bossDefeated`를 참으로만 재다가 그 줄을 지워도 통과하는 것을 봤다.

**갈래마다 결과를 다르게 읽으라.** 같은 「지워도 아무도 모른다」라도 무엇을
건드렸느냐에 따라 뜻이 다르다:

| 무엇을 훑나 | 이 저장소에서 나온 비율 | 결과를 어떻게 읽나 |
|---|---|---|
| **대입** (공유 객체에 쓰는 줄) | 109줄 중 71 → 2 | 거의 다 진짜다. 값이 화면에 안 닿는다는 뜻이라 바로 고치면 된다 |
| **조건** (이른 반환) | 216줄 중 5 | 대부분 **일어날 수 없는 상태를 막는 방어선**이다. 「닿을 수 있는가」부터 물으라 |
| **비교 방향** (`>` ↔ `<`) | 55줄 중 4 | 적중률이 높다 — 방향은 늘 결과를 바꾼다. 대신 **무한 반복**을 조심하라 |

훑을 순서를 고른다면 **대입 → 비교 → 조건**이다. 앞의 둘은 나온 것을 거의
그대로 믿을 수 있고, 조건은 하나하나 따져야 해서 품이 가장 많이 든다.

**배선은 손으로 찾지 말고 쓸어내라.** 공유 객체에 쓰는 줄을 전부 모아 하나씩
지우고 매번 전체 검사를 돌리면 된다. 이 저장소에서는 **60개 중 51개가 지워도
아무도 모르는** 상태였다 — 결함 모양 1위라는 것이 감이 아니라 숫자로 나온다.

**검사가 이름조차 부른 적 없는 export를 세라.** 523개 중 138개였고, 타입과
팔레트를 빼면 후보는 몇 안 된다 — 그 중 하나가 **입력**이었다. `consumeJump`가
큐를 안 비워도 통과했다(한 번 눌러 계속 떠오른다). 사람에게 가장 가까운 표면이
가장 비어 있을 수 있다.

**한 곳에서 찾은 결함 모양은 이웃에도 있다.** 보스 위상 타이머가 「전이만 보고
지속을 안 본다」로 뚫린 것을 찾은 뒤, 같은 자를 일반 적에게 대 보니 곧바로 또
나왔다 — 쓰러진 적이 두 프레임 만에 일어나도 검사가 몰랐다. 결함을 고친 뒤에는
**같은 모양이 어디 또 있는지** 한 번 더 훑으라.

**규칙이 결함 아닌 것을 물면 규칙을 좁히라 — 코드를 규칙에 맞추지 말고.**
한 세션에 두 번 걸렸다: 「delta를 받는 루프는 전부 잘라야 한다」는 사인 위상만
쓰는 루프를 물었고, 「인도 두께 0.16을 박지 마라」는 팔 두께·음량까지 물었다.
그리고 소스를 읽는 검사가 깨지면 **결함인지 이사인지부터 가르라** — 이사라면
검사를 따라 옮기지 말고 **값으로 재는 쪽으로 바꿀 기회**다.

**같은 규칙이 두 자리에 있으면 한 자리만 지켜진다.** 소스에서 똑같이 반복되는
줄을 세어(여기서는 278개) 각각 뒤집어 보라. 여정 기준값은 두 자리 중 한 자리만
검사가 있었고, delta 자르기는 다섯 자리 중 하나가 공유 상수 대신 숫자를 박고
있었다 — 그 상수의 주석이 「따로 두었더니 일곱 벌이 됐다」고 적은 바로 그 사고다.

**가장 명중률 높은 표적: 주석이 못 박았는데 아무도 안 지키는 규칙.**
`반드시`·`금지`·`~하면 안 된다`로 소스를 긁으면 코드베이스가 **스스로 어디가
중요한지 적어 둔 목록**이 나온다(여기서는 58곳). 값으로 잴 수 있는 것만 뒤집어
봐도 둘이 뚫렸다 — 하나는 「호출마다 새 객체를 돌려주면 무한 렌더」, 하나는
「아틀라스를 반복으로 감싸면 옆 칸 색이 샌다」. 둘 다 주석에 그렇게 적혀 있었다.

**표적 고르는 법 하나 더: 검사에 이름조차 안 나오는 소스를 찾으라.**
`ls src` 대 검사 전문을 맞대 보면 금방 좁혀진다. 103개 중 3개가 나왔고, 그 중
하나(`FilterOverlay`)에서 구멍 넷이 한꺼번에 나왔다 — 넷 다 **그 파일 주석이
이미 못 박은 제약**이었다. 글로만 있는 규칙은 지켜지지 않는다.

**두 번째 흔한 약점: 서식에 기대는 것.** 「지금 코드 모양」에 맞춰 쓰면 서식이
바뀌는 순간 **조용히 눈이 먼다.** 소스를 읽는 검사가 원래 약한 것이 아니다 —
이 저장소의 소스 14개에 주석을 끼워 봐도 기존 검사는 **하나도 안 깨진다.**
약한 것은 **급히 쓴 검사**다. 한 세션에 세 번 당했다 — `startClipRecording(canvas, 30`
처럼 **한 줄 호출을 전제한** 정규식(인자를 줄바꿈하자 죽었다), **400자 창**으로 자르다
렌더 줄을 놓친 것, `^\s+prop={`로 **줄머리에 묶어** 한 줄에 몰아 쓴 배선을 통째로
놓친 것. 공백을 견디게 쓰고, 창은 넉넉히 잡고, 줄머리에 묶지 마라.

**반대쪽도 재 보라 — 결함이 아닌 변화에는 견디는가.** 주석을 한 줄 끼우거나 인자를
줄바꿈해 보고 **여전히 통과하는지** 본다. 결함에만 무는 것이 좋은 검사이고, 서식만
바꿔도 깨지는 검사는 다음 사람이 **검사를 고치는 데** 시간을 쓰게 만든다. 한쪽만
재면 그런 검사를 좋은 검사로 착각한다.

그리고 **「헛돎」이 나오면 검사를 의심하기 전에 변이부터 본다.** 이름을 전체
치환하거나(정의와 호출이 함께 바뀌어 동작이 같다) 안 쓰는 상수를 더하면
통과하는 것이 맞다 — 변이는 **동작이 달라지는 것**이어야 한다.

### 검사끼리 새지 않는지

```bash
npx vitest run --sequence.shuffle
```

순서를 섞어 돌린다. 전역을 스텁하거나 저장소를 건드리는 검사가 늘면 **앞 검사가
남긴 상태에 기대는 검사**가 생기고, 그건 평소 순서에서는 늘 통과한다.
`pnpm verify`에는 넣지 않는다 — 검증은 되풀이 가능해야 하고, 섞는 것은 그 반대다.
**검사를 여러 개 더한 날 한 번 돌려 보는 용도다.**

`all` 대신 특정 검사 파일을 넣을 수도 있지만 되도록 `all`을 쓴다. 어느 검사가
그 규칙을 지키는지 모르는 채 한 파일만 돌리면 **없는 구멍을 보고한다** —
실제로 세 번 그랬다.

## 이 프로젝트의 특이한 점

**외부 에셋이 둘뿐이다** — 캐릭터 모델(`character.glb`)과 시작 화면 그림
(`title-street.webp`). 도시·소리·텍스처는 전부 코드로 만든다.

- 텍스처 → 런타임 캔버스 합성 (`src/game/world/textures.ts`)
- 사운드 → Web Audio 합성 (`src/game/systems/audio/`)
- 도시·도깨비·적 → 프리미티브 조합
- **플레이어 캐릭터 → GLB 하나** (`public/character.glb`, 1.1MB)

캐릭터만 예외로 들인 이유는 **사람 몸이 상자로 흉내 내기 가장 어렵기** 때문이다.
원본은 동작마다 파일이 따로여서 12개 68MB였는데, `scripts/build-character.mjs`가
하나로 합치고 텍스처를 2048px PNG → 1024px JPEG로 줄여 1.1MB로 만든다.

받는 동안과 실패했을 때는 **예전 절차적 캐릭터가 그대로 보인다**
(`src/game/player/Character.tsx`) — 캐릭터가 없으면 게임이 성립하지 않는다.

「0개」가 아니라 **「정해 둔 하나만」**이 지금 규칙이다. `tests/forbiddenApis.test.ts`가
목록에 없는 에셋과, 그 파일 밖에서 쓰는 로더를 막는다.

(`public/`에 Next.js 시작 템플릿의 SVG 다섯 개가 남아 있지만 **어디에서도
참조하지 않는다** — 지워도 되는 잔재다.)

초기 다운로드 예산 때문이다. 공통 번들은 **128KB gzip**이고 three.js 청크
314KB는 `/play`에 들어갈 때만 받는다.

**테스트가 화면 대신 눈 노릇을 한다.** 그중 상당수는 순수 로직이
아니라 **배치 정합성·수치 관계·자원 정리**를 검증한다. 도로 좌표가 반 칸
어긋나거나, 점프로 탄을 피할 수 없거나, 지오메트리가 해제되지 않는 것을
그 테스트들이 잡았다.

    core/       의존성 없는 유틸
