# DokeV 프로덕트 디자인 가이드

> 문서 상태: Draft v0.1  
> 최초 작성일: 2026-08-16  
> 마지막 수정일: 2026-08-23  
> 관련 문서: [PROJECT_PLAN.md](./PROJECT_PLAN.md)

## 1. 목적

이 문서는 DokeV를 일회성 3D 데모가 아니라 반복 개발과 운영이 가능한 실제 웹 프로덕트로 제공하기 위한 디자인 기준이다.

프로덕트 수준의 디자인은 다음 네 가지를 동시에 만족해야 한다.

1. 처음 방문한 사용자가 설명 없이 시작할 수 있다.
2. 데스크톱과 모바일에서 같은 경험을 각 입력 방식에 맞게 제공한다.
3. 로딩, 실패, 빈 상태, 재접속까지 모든 상태가 정의되어 있다.
4. 디자인 규칙이 코드와 테스트로 이어져 화면마다 달라지지 않는다.

## 세계관 — 도깨비란 무엇인가

> 이 절이 이 프로젝트에서 가장 먼저 정해진 것이다. 아래의 모든 규칙이 여기서 나온다.

**아이들의 세상에서는, 주변에 문제가 생기면 그것이 도깨비의 모습으로 보인다.**
그 도깨비를 물리치고 나면 친구가 된다.

어른의 눈에는 고장 난 자판기이고 시끄러운 공사장이고 어두워진 골목이다. 아이의
눈에는 그것이 **모습을 갖추고 서 있다.** 도깨비는 따로 사는 종족이 아니라
**문제가 보이는 방식**이다.

### 여기서 따라 나오는 것

| 규칙 | 왜 |
|---|---|
| **평소에는 도깨비가 없다** | 문제가 없으면 도깨비도 없다. 동료가 도시를 내내 따라다니면 이 말이 거짓이 된다 (`dokebi/summonWindow`) |
| **문제가 가까워지면 나타난다** | 등장 조건이 「전투」인 이유가 연출이 아니라 세계관이다 |
| **물리친 뒤 친구가 된다** | 이긴다는 것은 없애는 것이 아니라 **마주한다**는 뜻이다. 그래서 쓰러뜨린 자리에서 사라지지 않고 곁에 남는다 |
| **친구가 된 도깨비는 능력을 준다** | 넘어선 문제는 다음에 힘이 된다. 능력이 「보상」이 아니라 **그 문제의 성질 그대로**여야 하는 이유다 — 어두운 골목을 넘어선 아이는 어둠을 밝히는 법을 안다 |
| **죽지 않는다** | 문제 앞에서 지는 일은 있어도, 끝나는 일은 없다 |

### 대사가 지는 몫

**선택지도 분기도 없다.** 대사는 고르게 하려고 있는 것이 아니라 **위의 정의를
전하려고** 있다. 처음 도깨비를 만나는 자리에서 이 말이 나오지 않으면, 플레이어는
끝까지 「몬스터를 잡아 동료로 만드는 게임」으로 이해한다 — 그건 다른 게임이다.

## 2. 경험 원칙

### 2.1 세계가 먼저, UI는 나중에

- 플레이 중 고정 HUD는 현재 목표, 상호작용, 메뉴만 노출한다.
- 부가 정보는 사용자가 요청할 때 패널이나 도감에서 보여준다.
- 중요한 위치는 아이콘만 띄우지 않고 빛, 소리, NPC 시선, 환경 움직임으로도 안내한다.
- 3D 배경 위 텍스트에는 반투명 표면 또는 대비 보호 레이어를 둔다.

### 2.2 설명보다 행동으로 학습

- 첫 골목에서 이동, 첫 NPC 앞에서 상호작용을 자연스럽게 가르친다.
- 여러 조작법을 한 번에 설명하지 않는다.
- 입력 장치에 맞춰 키보드 키, 마우스, 터치 버튼을 자동 표시한다.
- 튜토리얼을 건너뛰거나 메뉴에서 다시 볼 수 있게 한다.

### 2.3 즉시 반응하고 결과를 명확히 표시

- 누름, 수집, 저장, 실패에는 100ms 안에 시각적 피드백을 시작한다.
- 진행 중인 비동기 작업에는 로딩 또는 진행 상태를 표시한다.
- 성공은 색상 외에 아이콘, 문구, 모션, 사운드 중 두 가지 이상으로 전달한다.
- 사용자가 취소하거나 다시 시도할 수 없는 긴 연출은 만들지 않는다.

### 2.4 즐거움은 선택 가능해야 함

- 배경음, 효과음, 카메라 흔들림, 모션 강도를 각각 조절한다.
- `prefers-reduced-motion`을 감지하고 저감 모션을 기본 적용한다.
- 자동 재생 사운드는 사용자의 첫 명시적 입력 이후 시작한다.
- 반복 플레이에서는 이미 본 연출을 건너뛸 수 있게 한다.

## 3. 정보 구조

```text
랜딩
├─ 체험 시작
│  ├─ 게스트 시작
│  └─ 이어하기
├─ 소식
├─ 세계관 소개
└─ 접근성/설정

월드
├─ 현재 퀘스트
├─ 지도
├─ 도감
├─ 포토 모드
├─ 프로필
└─ 설정/도움말

결과
├─ 획득 도깨비
├─ 사진 저장
├─ 공유
└─ 계속 탐험
```

### 내비게이션 규칙

- 랜딩의 주 행동은 `체험 시작` 하나로 유지한다.
- 월드에서는 `Esc` 또는 메뉴 버튼으로 모든 부가 기능에 접근한다.
- 모바일 메뉴는 전체 화면 패널, 데스크톱은 우측 사이드 패널을 기본으로 한다.
- 브라우저 뒤로 가기가 앱 종료처럼 작동하지 않도록 화면 상태와 URL을 연결한다.
- 도감, 프로필, 공유 결과는 직접 접근 가능한 URL을 제공한다.

## 4. 핵심 사용자 흐름

### 최초 방문

```text
랜딩 → 사운드 선택 → 기기 성능 자동 확인 → 캐릭터 선택
→ 이동 튜토리얼 → 첫 NPC → 단서 수집 → 미니게임
→ 도깨비 획득 → 포토 모드 → 저장/공유 → 계속 탐험
```

### 재방문

```text
랜딩 → 이어하기 → 마지막 안전 지점 → 오늘의 목표 또는 도감
```

### 성능 부족

```text
기기 확인 → 경량 모드 제안 → 품질 자동 조정
→ 그래도 실패하면 2D 세계관·도감 경험 제공
```

### 5.2 디자인 토큰

Figma 변수와 CSS 변수의 이름을 일치시킨다. 컴포넌트에서 임의의 색상이나 여백 값을 직접 사용하지 않는다.

```text
color.bg.canvas
color.bg.surface
color.bg.overlay
color.text.primary
color.text.secondary
color.text.inverse
color.action.primary
color.action.primary.hover
color.status.success
color.status.warning
color.status.danger

space.1 / 4px
space.2 / 8px
space.3 / 12px
space.4 / 16px
space.6 / 24px
space.8 / 32px

radius.sm / 8px
radius.md / 16px
radius.lg / 24px
radius.round / 999px

motion.fast / 120ms
motion.normal / 200ms
motion.slow / 320ms
```

초기 값은 출발점이며 실제 화면과 접근성 검증 후 조정한다.

### 5.3 색상

- 브랜드 색상과 기능 상태 색상을 분리한다.
- 본문 텍스트 대비는 WCAG 2.2 AA 기준 4.5:1 이상을 목표로 한다.
- 큰 텍스트와 주요 UI 윤곽은 최소 3:1을 목표로 한다.
- 색상만으로 퀘스트 완료, 오류, 희귀도를 구분하지 않는다.
- 3D 환경 변화에도 대비가 유지되도록 HUD 배경 보호 레이어를 제공한다.
- 라이트/다크 테마보다 `월드 HUD 테마`와 `메뉴 테마`를 우선 정의한다.

### 5.4 타이포그래피

- 한국어 본문 가독성을 우선하고 한글·영문·숫자 조합을 함께 검수한다.
- 본문은 모바일 기준 16px 이상을 기본으로 한다.
- 긴 대사는 2~3줄 단위로 나누고 사용자가 직접 넘기게 한다.
- 텍스트 200% 확대에서도 메뉴와 주요 흐름이 깨지지 않아야 한다.
- 이미지에 텍스트를 구워 넣지 않는다.
- 숫자나 남은 개수는 고정폭 숫자 옵션을 검토한다.

### 5.5 아이콘과 일러스트

- 24px 그리드를 기본으로 동일한 선 굵기와 모서리 규칙을 사용한다.
- 아이콘만 있는 버튼에는 접근 가능한 이름과 툴팁을 제공한다.
- 도깨비 카드 일러스트는 배경, 실루엣, 희귀도 프레임을 분리 제작한다.
- 장식 요소가 상호작용 요소처럼 보이지 않도록 명도와 깊이를 구분한다.

### 5.6 모션

- UI 피드백은 짧고 정확하게, 획득 연출만 의도적으로 크게 사용한다.
- 반복적으로 사용하는 버튼은 과도하게 튀거나 흔들리지 않는다.
- 화면 전환은 이동 관계를 설명할 때만 방향성을 사용한다.
- 모션 중에도 닫기, 건너뛰기, 다음 행동이 가능해야 한다.
- 저감 모션에서는 이동·확대 대신 페이드와 즉시 전환을 사용한다.

### 5.7 월드 룩 기준 (레퍼런스 무드보드)

이 절이 **월드가 무엇처럼 보여야 하는지의 정본**이다. 여기가 비어 있던 동안 생성 이미지(`assets/concepts/*-meshy-*.png`)가 기준 자리를 대신 차지했고, 그 결과 룩을 판단할 근거가 「생성물과 닮았는가」밖에 없었다. 새 에셋·구역·조명을 만들 때 먼저 이 절과 대조한다.

#### 기준 장면

펄어비스 「도깨비」 2021 Gamescom 트레일러의 **한옥 골목 장면** 한 컷. 기능 분석은 [TRAILER_FEATURE_ANALYSIS.md](./TRAILER_FEATURE_ANALYSIS.md)에 있고, 여기서는 **화면이 어떻게 보이는지**만 다룬다.

> 원작을 복제하기 위한 기준이 아니다. 「한국 동네를 아이가 뛰어다니는 화면」이 성립하는 조건을 뽑아낸 것이고, 우리는 그것을 브라우저에서 되는 범위로 옮긴다.

#### 그 장면에서 읽히는 것

| 요소 | 레퍼런스 | 우리가 취할 것 |
|---|---|---|
| 시간대 | 한낮 직사광. 나뭇잎 그림자가 판석에 선명하다 | `noon`을 룩의 기준 시간대로 둔다. 노을·밤은 변주다 |
| 눈높이 | 기와담장이 시야를 채우고 그 **너머로** 현대 건물이 선다 | 담과 문을 눈높이 요소로 쓴다. 담 없이 상가만 있는 화면은 이 기준에 미달이다 |
| 벽면 | 글자가 없다. 재질과 식생이 벽을 채운다 | 담이 선 구역에는 간판을 붙이지 않는다 (`cityDetails`가 `shrine`을 건너뛰는 이유) |
| 식생 | 화면의 약 3분의 1. 벚꽃·철쭉·담쟁이 | 담 위 담쟁이와 담 아래 화분을 담과 한 벌로 취급한다 |
| 인물 | 또래 아이들이 각자 다른 동작. 백팩·모자·보호대 | 배경 인물에 **동작 차이**를 먼저 준다. 소품은 그다음이다 |
| 바닥 | 밝은 회백색 판석. 담의 검은 기와와 대비를 만든다 | 밝은 바닥을 유지한다. 어두운 바닥에 회색 담을 세우면 화면이 통째로 가라앉는다 |

#### 우리 룩이 레퍼런스와 **다르기로 한** 것

닮게 만들 수 없는 것을 목표로 두면 매번 미달로 끝난다. 아래는 의도적인 차이다.

- **셀셰이딩 저폴리를 유지한다.** 브라우저에서 물리 기반 렌더와 손으로 모델링한 기와를 감당할 수 없다. 대신 색과 실루엣으로 승부한다.
- **톤매핑을 끈다.** ACES 필믹은 카툰 룩의 채도를 눌러 파스텔 벽을 바래게 만든다 (`GameScene`의 `NoToneMapping`).
- **담 높이는 1.8m를 넘지 않는다.** 넘으면 3인칭 카메라가 담 안으로 들어간다. 레퍼런스만큼 담을 높일 수 없으므로 **높이 대신 변 수와 길이**로 둘러싸인 느낌을 만든다.

#### 에셋 판정 기준

- 생성 이미지(Meshy 등)는 **탐색용 스케치**로만 쓴다. 그대로 룩의 기준이 되면 그 위에 무엇을 얹어도 생성물 인상이 남는다.
- 새 에셋은 위 표의 「우리가 취할 것」과 대조해 판정한다. 「레퍼런스와 닮았는가」가 아니라 **「그 조건을 만족하는가」**가 기준이다.

## 6. 반응형 및 입력 설계

### 기준 뷰포트

다음 크기를 대표 검수점으로 사용하되, 고정 레이아웃이 아니라 유동 레이아웃으로 구현한다.

| 구분 | 대표 검수 크기 | 기본 입력 |
|---|---:|---|
| Mobile compact | 360×800 | 터치 |
| Mobile large | 430×932 | 터치 |
| Tablet | 768×1024 | 터치/키보드 |
| Laptop | 1366×768 | 키보드/마우스 |
| Desktop | 1920×1080 | 키보드/마우스 |
| Ultrawide | 2560×1080 | 키보드/마우스 |

### 레이아웃 규칙

- HUD는 화면 모서리가 아니라 safe area 토큰을 기준으로 배치한다.
- 모바일 터치 영역은 최소 44×44 CSS px을 목표로 한다.
- 주요 버튼끼리 최소 8px 간격을 둔다.
- 3D 조작 영역과 OS 제스처 영역이 충돌하지 않게 한다.
- 세로 모바일을 기본 지원하고, 가로 모드는 별도 HUD 배열을 정의한다.
- 울트라와이드에서는 정보가 모서리로 지나치게 벌어지지 않도록 최대 HUD 폭을 둔다.

### 입력 방식

| 행동 | 키보드/마우스 | 터치 |
|---|---|---|
| 이동 | WASD/방향키 | 좌측 가상 스틱 |
| 시점 | 마우스 드래그 | 우측 화면 드래그 |
| 살펴보기 | T | 「살펴보기」 버튼 |
| 점프·활강 | Space (누르고 있으면 활강) | 점프 버튼 |
| 동료 능력 | E | 능력 버튼 |
| 패널 닫기 | Esc | 「닫기」 버튼 |
| 포토 모드 | P/「사진」 버튼 | 「사진」 버튼 |

키 재설정은 MVP 이후라도 입력 구조 자체는 리매핑 가능하게 설계한다.

이 표는 **정본이 아니다.** 실제 키는 `src/game/systems/controls.ts`의
`CONTROL_CODES` 하나뿐이고, 여기 적힌 글자가 그것과 어긋나면 검사가 막는다 —
예전에는 「상호작용 E」라고 적혀 있었는데 `E`는 동료 능력이고 살펴보기는 `T`였다.
전체 목록은 게임 화면 아래 조작 안내가 정본에서 만들어 보여 준다.

## 7. 3D 월드와 UI의 결합

### 레이어

1. World layer: 지형, 건물, 캐릭터, 도깨비
2. Diegetic layer: 월드 안 간판, 단서 빛, NPC 말풍선
3. HUD layer: 목표, 상호작용, 조작
4. Product layer: 로그인, 설정, 오류, 정책, 공유

Product layer는 일반 HTML DOM으로 구현해 접근성과 복구 가능성을 확보한다. 게임 진행에 필수적인 텍스트를 WebGL 캔버스 안에만 넣지 않는다.

### 카메라

- 카메라 민감도, Y축 반전, 흔들림 설정을 제공한다.
- 벽 충돌과 좁은 공간에서 급격한 줌 변화를 완화한다.
- 퀘스트 안내가 사용자의 카메라 제어권을 오래 빼앗지 않게 한다.
- 멀미를 줄이기 위해 기본 FOV와 가속도를 보수적으로 설정한다.

### 월드 안내

- 목표까지 직선을 그리는 대신 가까운 환경 단서를 단계적으로 사용한다.
- 길을 잃으면 일정 시간 후 선택적인 힌트를 제공한다.
- 화면 밖 중요 사운드에는 방향 표시를 함께 제공한다.
- 상호작용 가능 거리에 진입하면 오브젝트 강조와 입력 힌트를 동시에 표시한다.

## 8. 컴포넌트 상태 명세

모든 인터랙티브 컴포넌트는 다음 상태를 디자인하고 구현한다.

- Default
- Hover: 포인터 장치에만 적용
- Focus-visible
- Pressed
- Selected
- Disabled
- Loading
- Success
- Error

### 버튼 완료 조건

- 레이블이 행동을 명확히 설명한다.
- 기본, 보조, 위험 행동의 위계가 구분된다.
- 키보드 포커스가 명확하고 오버레이에 가리지 않는다.
- 로딩 중 중복 실행을 막되 진행 중임을 알린다.
- 오류 발생 시 원인과 재시도 방법을 버튼 가까이에 표시한다.

## 9. 반드시 디자인할 서비스 상태

### 시스템 상태

- 최초 로딩
- 구역 추가 로딩
- 느린 네트워크
- 오프라인 전환
- WebGL 미지원
- GPU 또는 메모리 부족
- 서버 오류
- 점검 중
- 새 버전 배포로 인한 갱신 요청

### 데이터 상태

- 신규 사용자
- 저장 데이터 있음
- 저장 중
- 저장 완료
- 저장 충돌
- 저장 실패 및 로컬 복구
- 도감이 비어 있음
- 검색 결과 없음
- 공유 링크 만료 또는 존재하지 않음

### 권한 상태

- 사운드 재생 대기
- 전체 화면 요청 거절
- 클립보드/공유 API 미지원
- 사진 저장 실패
- 세션 만료

각 오류 화면은 `무슨 일이 발생했는지`, `진행 정보가 안전한지`, `사용자가 다음에 무엇을 할 수 있는지`를 포함한다.

## 10. 접근성 기준

목표 적합 수준은 WCAG 2.2 AA로 한다.

- 키보드만으로 랜딩, 설정, 퀘스트, 도감, 포토 모드 이용
- 논리적인 포커스 순서와 항상 보이는 포커스 표시
- 화면 낭독기가 이해할 수 있는 이름, 역할, 상태
- 텍스트 대비 4.5:1 이상, 큰 텍스트 3:1 이상
- 텍스트 200% 확대 지원
- 색상·소리·위치 중 하나에만 의존하지 않는 안내
- 대사 및 영상 자막
- 카메라 흔들림, 모션 블러, 섬광, 배경 모션 끄기
- 시간 제한이 있는 미니게임의 완화 옵션
- 드래그 동작의 버튼 대안

자동 검사는 첫 방어선이며, 키보드·화면 낭독기·실기기 수동 검수를 별도로 진행한다.

## 11. 성능도 디자인 요구사항이다

### 공개 품질 게이트

- LCP: 2.5초 이하
- INP: 200ms 이하
- CLS: 0.1 이하
- 실제 사용자 데이터의 모바일·데스크톱 75백분위 기준으로 측정
- 월드 진입 전 현재 로딩 단계와 예상 진행을 표시
- 느린 기기에서는 품질을 자동 낮추고 선택권을 제공

랜딩 페이지의 Core Web Vitals와 3D 월드의 FPS·메모리·로딩 시간은 별도 대시보드로 관리한다.

- 디자인 상태가 모두 정의됨
- 반응형 동작이 정의됨

3. 접근성 리뷰: 키보드, 대비, 낭독, 모션 옵션
4. 성능 리뷰: 로딩, FPS, 입력 지연
5. 실기기 리뷰: 대표 모바일과 데스크톱

## 14. 출시 전 디자인 QA

### 공통

- [ ] 모든 페이지에 로딩·빈 상태·오류 상태가 있다.
- [ ] 버튼 레이블과 실제 동작이 일치한다.
- [ ] 브라우저 뒤로 가기와 새로고침 후 상태가 자연스럽다.
- [ ] 토스트가 중요한 오류의 유일한 안내 수단이 아니다.
- [ ] 실제 한국어 문장으로 잘림과 줄바꿈을 확인했다.

### 반응형

- [ ] 대표 6개 뷰포트에서 검수했다.
- [ ] safe area와 모바일 브라우저 UI를 고려했다.
- [ ] 가상 키보드가 입력 필드를 가리지 않는다.
- [ ] 화면 회전 후 조작과 레이아웃이 복구된다.
- [ ] 울트라와이드에서 HUD가 과도하게 벌어지지 않는다.

### 접근성

- [ ] 키보드만으로 핵심 플로우를 완주했다.
- [ ] 포커스가 오버레이 뒤로 빠지지 않는다.
- [ ] WCAG 2.2 AA 자동 검사와 수동 검사를 수행했다.
- [ ] 200% 확대에서 콘텐츠 손실이 없다.
- [ ] 저감 모션과 무음 상태에서도 진행할 수 있다.

### 3D 경험

- [ ] 사용자가 카메라 제어권을 잃는 구간이 최소화되었다.
- [ ] 상호작용 가능 대상이 배경과 구분된다.
- [ ] 저사양 모드에서도 목표와 단서가 보인다.
- [ ] 월드 로딩 실패 시 재시도와 2D 대안이 있다.
- [ ] 장시간 플레이 후 메모리와 프레임을 확인했다.
